# 第 20～36 章改寫前後的實際對照

2026 年 11 月 4 日（台灣時間），17 章共 84 次執行全部通過。相同案例共有 41 組前後執行（82 次）；另有 2 次 Repository Fake 的補充檢查。前後的實際輸入與結果也經程式比對一致，不只比較綠燈數量。

## 重現步驟

先依 [chapters 的環境說明](../../../tests/e2e/chapters/README.md) 安裝後端、前端與測試套件，啟用後端 Python 環境。在範例專案根目錄執行：

```bash
cd tests/e2e/chapters
npm run chapter -- 23
npm run chapter -- all
```

單章與 all 都會先執行改寫前，再執行改寫後。兩邊各自啟動 Playwright，從同一份初始資料庫快照複製出獨立資料庫；不會使用前一組已修改的資料。所有執行均不重試，第 34 章前後各用一個、兩個 worker；第 35 章前後各重複二十次。

## 來源與公平比較

原始 v1、v2 的檔案逐一核對，保持本輪開始前的內容。各章的改寫前是從 v1 擷取流程、統一帳號及輸入，再與改寫後共用驗收與留證步驟的教學對照，不是原始 v1 的逐字副本。來源及延伸情境均見 [逐章素材表](../chapter-example-map.md) 與各章 COMPARISON.md。

餐點案例兩邊都確認原有資料、從網頁修改價格、同一餐點更新、其他欄位不變、沒有重複新增，並重新開啟編輯頁面。這些完整檢查有部分是從原始 v1 再補上的，但兩邊一致。資料準備與查詢使用真實 API，價格仍由網頁修改。

前後比對會比較欄位值、預期價格、查詢結果與筆數；兩邊各自在測試中確認餐點編號前後一致。平行執行時，資料庫配號順序可能不同，因此不要求兩輪的編號相等。編號並沒有從個別測試的驗收中移除。

Object Mother 使用 FIND-T03 的搜尋與待取餐篩選流程；網路模擬使用 MEAL-T06 的失敗保留輸入及重新送出流程。角色認證、Repository 與 Fake 的資料存取檢查另行標示為 API 延伸，沒有算成網頁 E2E。
