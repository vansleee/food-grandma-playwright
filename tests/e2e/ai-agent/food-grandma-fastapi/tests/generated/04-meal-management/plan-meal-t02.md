# MEAL-T02：修改既有餐點價格的測試計畫

## 測試目的

確認餐廳管理者能從編輯頁，將一筆餐點的價格由 120 改為 150。修改的是原餐點，不是新增另一筆。

依據 `specs/04-meal-management.md` 的 MEAL-04，這次要確認：

- 編輯頁先顯示正確的原有資料。
- 儲存後，同一個餐點編號的價格更新為 150。
- 沒有因為儲存而重複新增餐點。

另外檢查名稱與描述保持原值，重新開啟編輯頁後價格仍為 150。本次不測無效輸入、儲存失敗、搜尋或不同餐廳之間的權限。

## 執行前準備

- 本機管理網站與後端已啟動，示範餐廳帳號可以登入。
- 本次使用已登入的管理頁面；登入表單本身不在測試範圍。
- 每次執行都新增一筆專用餐點，不使用先前探索留下的資料。
- 執行期間，避免其他人或程序同時新增、刪除或修改這間餐廳的餐點。

| 測試資料 | 內容 |
|---|---|
| 名稱 | 包含本次執行識別碼，能與其他餐點區分 |
| 描述 | 填入本次可辨識的描述，儲存後用來比較是否保持原值 |
| 圖片網址 | 留空 |
| 原價格 | 120 |
| 新價格 | 150 |
| 餐點編號 | 使用建立餐點時系統回傳的編號，不寫死示範編號 |

## 測試步驟與預期結果

| 步驟 | 要做的事情 | 預期結果 |
|---|---|---|
| 1．建立專用餐點 | 透過 API 建立價格 120 的餐點，記錄回傳的編號與完整內容；建立完成後再查詢餐點列表，記錄編號集合 | 專用餐點建立成功，資料與輸入一致，列表包含該編號 |
| 2．開啟餐點列表 | 進入餐點管理頁，依剛才的編號找到餐點 | 該列顯示正確名稱、描述與價格 120 |
| 3．開啟編輯頁 | 點擊該列的餐點名稱，等待原有資料載入 | 開啟的是同一筆餐點，表單顯示原名稱、描述與價格 120 |
| 4．修改並儲存 | 只將價格改為 150，按下「儲存餐點」 | 頁面發出的更新請求指向原餐點；回應成功，包含同一個編號與價格 150 |
| 5．確認列表 | 等待返回餐點列表並載入更新後的資料 | 同一筆餐點顯示價格 150，名稱與描述沒有改變 |
| 6．查詢儲存結果 | 透過 API 查詢原餐點及餐點列表，與修改前記錄的資料比較 | 原餐點只有價格改為 150；餐點編號集合不變，專用名稱仍只有一筆 |
| 7．重新開啟編輯頁 | 再次開啟原餐點的編輯頁，等待資料載入 | 名稱與描述仍為原值，價格為 150 |

步驟 1 的餐點列表必須在建立專用餐點之後記錄，才能與修改價格後的列表比較。建立測試資料本來就會增加一筆，不應把這一筆誤判為修改價格造成的重複新增。

步驟 3 要等待表單顯示原名稱與原價格，再開始輸入。只看到輸入欄出現，還不能確定餐點資料已載入。

## 如何確認三項驗收標準

| 驗收標準 | 檢查方式 | 需要記錄的資料 |
|---|---|---|
| 原有資料正確載入 | 比較編輯頁欄位與建立時的資料 | 餐點編號、原名稱、描述及價格 120 |
| 更新原餐點 | 從畫面修改價格，檢查更新回應，再查詢同一筆餐點 | 更新請求指向的編號、回應內容及重新查詢後的價格 150 |
| 不重複新增 | 比較修改前後的餐點編號集合，並確認專用名稱只有一筆 | 修改前後的餐點列表 |

只有 HTTP 200 不代表修改成功，也要檢查回應是否表示失敗，以及餐點編號與價格是否正確。不要求成功回應只能包含固定幾個欄位。

## 畫面與 API 的分工

- **畫面操作**：從列表開啟編輯頁、確認原有資料、修改價格、按下儲存，以及重新開啟編輯頁。
- **API 協助**：建立專用資料、查詢原餐點及餐點列表，並取得儲存後的資料作比較。
- **更新請求**：由畫面的儲存按鈕觸發，不直接用 API 改好價格後再查看畫面。

## 測試實作安排

沿用同目錄中已存在的程式，不另建重複功能。以下路徑均相對於這份計畫所在的目錄。

| 檔案 | 用途 |
|---|---|
| `support/fixtures.ts` | 取得餐廳認證，提供已登入的頁面、API Repository 與頁面物件，並釋放 API context |
| `support/restaurant-meals.ts` | 建立及查詢餐點 |
| `support/meals-page.ts` | 從列表依編號找到餐點，開啟編輯頁與檢查列內容 |
| `support/meal-form-page.ts` | 等待表單原值載入，填寫價格、儲存及檢查欄位 |
| `e2e/edit-meal-price.spec.ts` | 串起步驟，保留本次預期結果的檢查 |

資料建立仍由測試呼叫 Repository 執行。若現有方法不足，先指出需要補上的部分，再依上述分工調整。等待條件使用頁面路徑、欄位值或請求回應，不使用固定等待時間。

本次沿用現有 Fixture，以 API 登入取得的認證建立已登入頁面，不重複測試登入表單。

- 不重設共用資料庫，不修改既有餐點。這次沒有刪除餐點的 API，新增資料保留並記錄編號，不自行發明刪除方式。

執行後記錄餐點編號、修改前後資料、各項檢查結果，以及失敗時的錯誤資訊。計畫中的預期結果不是測試通過紀錄，仍須產生或調整程式並實際執行。
