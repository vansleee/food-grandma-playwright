# 第 15、16 章手寫與 Generator 對照

兩版使用同一份[測試計畫](plan.md)和[資料準備程式](../../support/ch15-16-comparison.ts)。每支測試都重新建立練習資料。三支測試分別驗證餐廳登入、指定訂單備餐完成，以及外送員確認送達後，餐廳查到同一筆訂單已送達。

## 執行方式

先依[各章執行說明](../../README.md#第一部分的-api-與-ui-練習)啟動本機 Food Grandma。API 使用 8081，網站使用 8082。兩組測試會重設資料，請各自依序執行，並使用可重設的本機練習資料庫。

在 `tests/e2e/chapters` 執行：

```text
npx playwright test -c playwright.first-part.config.ts ch15/comparison/ui-manual.spec.ts
npx playwright test -c playwright.agent-loop.config.ts ch16/comparison --grep CH15-T
```

第二條指令只跑三個對照案例。`seed.spec.ts` 是 Generator 探索時的起點。

| 版本 | 本次結果 |
| --- | --- |
| 第 15 章手寫版 | 3 passed（20.7 秒） |
| 第 16 章 Generator 原始產出，使用 MCP 執行 | 3 passed（20.2 秒） |

實測使用 macOS、Claude Code 2.1.311、Claude Sonnet 5.5 和 Playwright 1.63.0。兩版皆使用一個 worker，零重試。表中的秒數是當次測試的執行時間。

## Generator 取得的資料

手寫版寫完並執行後，另開 Claude Code 對話。[提示詞](prompt.txt)、計畫、種子測試、共用資料程式與執行設定放在獨立的練習副本。對話只開放 Playwright MCP 工具，沒有第二部分書稿、手寫版或舊的測試範例。Generator 使用瀏覽器工具查看網站，透過 `generator_write_test` 寫了三個檔案，再用 `test_run` 執行。範例保留這三個檔案的原始程式碼。

## 用第二部分的觀念讀程式碼

| 案例 | 手寫版 | Generator 版 | 可以討論什麼 |
| --- | --- | --- | --- |
| CH15-T01 簡單，登入後看到訂單管理 | 沿用 `SignInPage`，測試保留網址、標題與表格的檢查。 | 直接列出填帳密及按下登入的動作，第一次讀時可以順著步驟走。三個檔案各寫了一遍。 | 第 17 章 POM。只有登入測試時，直接寫就很清楚。備餐與送達也要登入時，修改按鈕定位只要改共用的頁面物件。 |
| CH15-T02 進階，指定訂單變成待取餐 | 用 `data-order-id` 找唯一一列，精確檢查該列的狀態欄。 | 用畫面顯示的訂單編號找列，對整列檢查文字，並確認按鈕已消失。 | 第 18 章定位與等待，以及第 20 章訂單列的責任。兩版都用這次資料的編號，也都用 Playwright 的條件等待。精確檢查狀態欄，失敗時更容易看出是哪個欄位出問題。 |
| CH15-T03 困難，跨角色確認送達 | 餐廳與外送員使用獨立瀏覽器環境。外送員的按鈕限縮在指定配送卡片裡，並在 `finally` 關閉外送員的環境。 | 也建立獨立環境並核對同一筆訂單。先確認配送標題，再點頁面上的送達按鈕。測試執行到最後才關閉外送員環境。 | 第 22、23 章的角色分工和 Fixture 清理。驗收中途失敗時，`finally` 仍會執行。將按鈕定位在同一張卡片，也能在日後畫面有多筆配送時維持操作範圍。 |

兩版都使用本次實驗提供的 Fixture。送達案例只出現一次，把誰操作、誰查結果留在測試裡就能讀懂。等到多支測試開始共用外送員的登入或配送步驟，再考慮把那段流程整理成可共用的方法。
