# 訂單搜尋、狀態篩選與空狀態

狀態：依現有實作整理，待人工核准；未執行驗證。共用前提見 [README](README.md)。

## 目的與範圍

餐廳在 `/management/orders` 找到需要處理的訂單。涵蓋列表、搜尋、狀態篩選、重新整理；不包含後端分頁、排序切換或訂單狀態修改。

## 規則

- FIND-01：清單只顯示已登入餐廳的訂單。API 目前依訂單 ID 遞減排序。
- FIND-02：搜尋比對訂單的原始數字 ID、顧客姓名或送達地址，忽略大小寫，去除查詢前後空白，採包含比對。
- FIND-03：狀態選項為全部、備餐中、待取餐、配送中、已送達；搜尋與狀態篩選同時成立才顯示。
- FIND-04：頁尾筆數反映篩選後結果；狀態頁籤筆數反映整份已載入清單，不隨搜尋文字縮減。
- FIND-05：有訂單但無符合結果時顯示「沒有符合條件的訂單，請調整搜尋或篩選。」；餐廳完全無訂單時顯示「目前還沒有訂單，新的訂單會顯示在這裡。」。
- FIND-06：首次載入期間顯示「正在載入訂單…」。載入失敗顯示錯誤，不得將錯誤解讀成成功的空清單。
- FIND-07：「重新整理」重新取得資料，載入期間按鈕停用；目前搜尋與篩選保留。

## 資料設計

建立可明確區分的訂單資料：餐廳 A 至少有 Cooking 與 Ready 各一筆，顧客／地址含可識別字串；餐廳 B 有另一筆訂單。從真實 API 取得資料與 ID。搜尋規則的組合測試可使用固定 response Stub；跨餐廳隔離必須以真實 API 驗證。沒有訂單的餐廳可用新餐廳帳號，不必清空其他測試資料。

## 驗收情境

| 案例 ID | 操作 | 預期結果 | 規則／層級 |
|---|---|---|---|
| FIND-T01 | A 查詢訂單 | 只含 A 的訂單，不含 B 的 ID | FIND-01／API |
| FIND-T02 | 分別輸入 ID、姓名、地址片段 | 顯示相應訂單；英文大小寫及前後空白依規則處理 | FIND-02／UI DDT |
| FIND-T03 | 搜尋顧客後選「待取餐」 | 僅顯示同時匹配顧客與 Ready 的列 | FIND-03／UI |
| FIND-T04 | 改搜尋条件 | 頁尾筆數更新；頁籤仍顯示未搜尋前各狀態總數 | FIND-04／UI |
| FIND-T05 | 搜尋不存在的字串 | 無訂單列，顯示無符合結果訊息 | FIND-05／UI |
| FIND-T06 | 空訂單餐廳載入完成 | 顯示尚無訂單，而非搜尋無結果 | FIND-05／UI |
| FIND-T07 | 控制首次回應延遲／失敗 | 分別顯示載入／錯誤，失敗不顯示成功空狀態 | FIND-06／Stub UI |
| FIND-T08 | 固定篩選後重新整理 | 發出新請求，完成後依原條件顯示新資料 | FIND-07／受控 UI |

## 技術契約

- `GET /api/restaurant/orders/`，Bearer token；回傳 `{ orders: [...] }`。
- API 狀態與 UI：Cooking→備餐中、Ready→待取餐、On the way→配送中、Delivered→已送達。
- 搜尋為前端過濾，沒有另外的搜尋 endpoint。
- 定位契約：`搜尋訂單` accessible name、頁籤 `aria-pressed`、`order-row`、`data-order-id`、`order-status`。

## 待確認與限制

- 顯示 ID 會補零並加 `#`，搜尋卻使用原始數字 ID。輸入畫面上的 `#0001` 不保證匹配；這是待確認的 UX 差異，不能讓 AI 默默改成新需求。
- 重新整理錯誤時可能仍保留舊資料，不能把舊資料解讀成最新結果。
