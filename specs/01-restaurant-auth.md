# 外送員接單權限規格

## 目的與範圍

本範例示範如何把一條角色權限需求寫成可審查、可測試的規格。Food Grandma 有顧客、外送員與店家管理者三種角色；這裡先聚焦外送員接單，不在第一個範例中展開完整權限矩陣、所有角色組合或跨角色旅程。

## 角色與前提

- **角色**：外送員。
- **目標操作**：接取一筆尚未指派的待取餐訂單。
- **測試資料**：一筆狀態為 `Ready`、尚未指派外送員的訂單；一個有效外送員存取權杖。
- **現況線索**：配套 API `POST /api/driver/orders/{order_id}/claim` 會檢查訂單狀態、指派狀況及外送員是否已有未完成配送。

## 業務規則

- ROLE-01：外送員可接取狀態為 `Ready` 且尚未指派的訂單；成功後，訂單狀態變為 `On the way`，並記錄接單的外送員。
- ROLE-02：若訂單不是 `Ready`、已指派給其他外送員，或目前外送員已有未完成配送，接單不得改變訂單狀態或指派對象。

## 驗收情境

只有在 ROLE-01、ROLE-02 經審查確認後，才將下列預期作為正式測試判準。下列案例是測試設計示例，尚未代表已執行或通過。

| 案例 ID | Given | When | Then | 驗證方式 |
|---|---|---|---|---|
| ROLE-T01 | 外送員已進入「可接訂單」頁，沒有進行中配送；一筆尚未指派的待取餐訂單顯示在列表中 | 點選該筆訂單的「接取訂單」 | 接單成功後進入「進行中配送」頁，顯示該筆訂單、「配送中」及「確認已送達」操作 | E2E；確認頁面導向與訂單資訊，並以訂單資料回讀接單者及狀態 |
| ROLE-T02 | 外送員 B 已有一筆進行中配送；「可接訂單」列表另有一筆未指派的待取餐訂單 | B 點選另一筆訂單的「接取訂單」 | 接單被拒，留在「可接訂單」頁，顯示 `Your outstanding order is not delivered yet.`；原配送仍屬於 B，另一筆訂單仍未指派 | E2E；確認畫面提示，並以訂單資料回讀兩筆訂單的狀態及指派者 |

介面主要使用中文標示；`Ready`、`On the way` 是後端狀態值，不是畫面文字。ROLE-T02 驗證外送員已有進行中配送時再次接單的畫面行為；目前 API 回傳 `Your outstanding order is not delivered yet.`，前端會直接顯示這段英文訊息。

## 測試資料與技術線索

- 接單 API：`POST /api/driver/orders/{order_id}/claim`，以 form 欄位傳入 `access_token`。
- 測試應使用可重建的專用資料；不可依賴列表第一筆訂單或其他案例留下的狀態。
- 產品規則核准前，可將案例當作測試設計草稿；不得讓 AI 自行把待確認要求改成確定的通過條件。
- 目前 API 的失敗回應與 HTTP 狀態需由實際查證確認；測試仍應回讀訂單，避免只看回應訊息。

## 與後續章節的連結

本章先用一個角色、一項操作建立規格到測試的基本流程。後續再逐步加入顧客與店家管理者、其他權限組合及跨角色旅程；第 31 章再以 Strategy 封裝不同角色的認證方式，並以 Adapter 統一不同角色的 API 介面。
